# MachineMandi Proof Protocol (EIP-712)

This document specifies the cryptographic proof protocol used between IoT machine devices, off-chain relayers/backends, and the on-chain `MachineMandi` smart contract.

---

## 1. Protocol Overview

MachineMandi uses **EIP-712 (Typed Structured Data Hashing and Signing)** to verify machine execution proofs on-chain. When a physical machine completes a paid task, its firmware creates and signs a typed message (`WorkProof`) with its private device key. An off-chain relayer or client submits this signed proof to `MachineMandi.submitProof(...)` to release escrowed funds to the node payout wallet.

---

## 2. EIP-712 Domain Specification

To prevent signature collision across different applications, contracts, or blockchain networks, all signatures must strictly adhere to the following EIP-712 domain separator:

| Field | Type | Expected Value | Description |
| :--- | :--- | :--- | :--- |
| `name` | `string` | `"MachineMandi"` | The human-readable name of the signing protocol |
| `version` | `string` | `"1"` | The current protocol version |
| `chainId` | `uint256` | Runtime chain ID | The EIP-155 chain ID of the active network (e.g., 31337 for local Hardhat) |
| `verifyingContract` | `address` | Deployed contract address | The exact on-chain address of the `MachineMandi` contract |

> **Critical Rule:** Both firmware and backend relayers must ensure `chainId` and `verifyingContract` match the actual deployed network and target contract. Any deviation results in signature rejection (`InvalidSigner`).

---

## 3. Typed Data Definition: `WorkProof`

The typed structure must be defined **exactly** as follows, in this **exact field order** without renaming or reordering:

```text
WorkProof(uint256 jobId,uint256 nodeId,uint256 nonce,uint256 startedAt,uint256 completedAt,uint256 preReading,uint256 postReading,bytes32 serviceHash)
```

The on-chain contract calculates the typehash via:
```solidity
bytes32 public constant WORK_PROOF_TYPEHASH = keccak256(
    "WorkProof(uint256 jobId,uint256 nodeId,uint256 nonce,uint256 startedAt,uint256 completedAt,uint256 preReading,uint256 postReading,bytes32 serviceHash)"
);
```

### Field Definitions & Meanings

| # | Field Name | Solidity Type | Meaning & Constraints |
| :-: | :--- | :--- | :--- |
| 1 | `jobId` | `uint256` | The unique on-chain job identifier created in `createJob` |
| 2 | `nodeId` | `uint256` | The unique on-chain node identifier matching `job.nodeId` |
| 3 | `nonce` | `uint256` | The unique job nonce generated at creation (`job.nonce`) |
| 4 | `startedAt` | `uint256` | Unix timestamp (seconds) when the machine began work |
| 5 | `completedAt` | `uint256` | Unix timestamp (seconds) when work finished; must satisfy `completedAt >= startedAt` |
| 6 | `preReading` | `uint256` | Initial sensor/meter reading prior to task execution |
| 7 | `postReading` | `uint256` | Final sensor/meter reading after task execution; must satisfy `postReading > preReading` and `postReading - preReading >= minDelta` |
| 8 | `serviceHash` | `bytes32` | The 32-byte cryptographic hash of the service specification matching `job.serviceHash` |

## 4. On-Chain Submission: `submitProof`

The smart contract function signature to submit this proof is:

```solidity
function submitProof(
    uint256 jobId,
    uint256 nodeId,
    uint256 nonce,
    uint256 startedAt,
    uint256 completedAt,
    uint256 preReading,
    uint256 postReading,
    bytes32 serviceHash,
    bytes calldata signature
) external nonReentrant
```

### Parameter Order
1. `jobId` (`uint256`)
2. `nodeId` (`uint256`)
3. `nonce` (`uint256`)
4. `startedAt` (`uint256`)
5. `completedAt` (`uint256`)
6. `preReading` (`uint256`)
7. `postReading` (`uint256`)
8. `serviceHash` (`bytes32`)
9. `signature` (`bytes`) — The 65-byte standard `(r, s, v)` ECDSA signature generated by the device signer key over the EIP-712 typed-data hash.

---

## 5. Integration Responsibilities

### Firmware Responsibilities
1. **Identical Typed Schema**: The firmware must encode the domain and `WorkProof` types with the exact field names, types, casing, and sequence defined above.
2. **Local Key Signing**: The private key corresponding to the node's registered `signer` address must reside securely inside the device (e.g., Secure Element / ATECC608 / hardware wallet) and never be exposed over the network.
3. **Sensor Reading Validation**: Firmware must measure and record `preReading` before task initiation and `postReading` upon task completion, verifying that `postReading > preReading`.

### Backend & Relayer Responsibilities
1. **Pass-Through Relaying**: The backend / relayer acts as an untrusted forwarder. It receives the proof parameters and `signature` from the device and submits them to `MachineMandi.submitProof(...)`.
2. **Zero Modification**: The backend must never alter field values, order, or signature bytes. Any modification will cause `ECDSA.recover` to produce a wrong address, reverting with `InvalidSigner`.
3. **No Domain Alterations**: The backend must not change domain name, version, chain ID, or verifying contract address.

---

## 6. Cryptographic Guarantee vs. Physical Reality

> [!IMPORTANT]
> **What the signature proves:** A successful cryptographic verification on-chain guarantees that **an entity possessing the private key of the registered `node.signer` produced an authentic signature over this exact payload**.
> 
> **What the signature DOES NOT prove:** The signature does **not** provide independent, infallible proof of physical-world reality. It cannot detect if:
> - Physical sensors were tampered with, spoofed, or bypassed prior to reporting readings.
> - The private key was extracted from insecure hardware.
> - Fluid or mechanical output diverged from sensor readings.
>
> On-chain verification establishes tamper-evident cryptographic accountability for the registered device identity.

## 8. Compatibility Testing Checklist

Before deploying or connecting a new firmware version or backend relayer, verify:

- [ ] **Domain Name**: String is exactly `"MachineMandi"` (case-sensitive).
- [ ] **Domain Version**: String is exactly `"1"`.
- [ ] **Chain ID**: Dynamic runtime value matches `block.chainid` (e.g., local hardhat node = 31337).
- [ ] **Verifying Contract**: Address strictly matches the deployed `MachineMandi` instance.
- [ ] **Type Name**: Typed struct is named `"WorkProof"`.
- [ ] **Field Count & Order**: All 8 fields match the exact order: `jobId`, `nodeId`, `nonce`, `startedAt`, `completedAt`, `preReading`, `postReading`, `serviceHash`.
- [ ] **Service Hash**: Matches the 32-byte hash snapshotted in `Job.serviceHash`.
- [ ] **Delta Threshold**: `postReading - preReading >= job.minDelta`.
- [ ] **Timestamp Order**: `completedAt >= startedAt`.
- [ ] **Deadline Check**: Submission reaches the blockchain while `block.timestamp <= job.deadline`.
- [ ] **Signature Format**: 65-byte serialized `r` (32 bytes) + `s` (32 bytes) + `v` (1 byte).
